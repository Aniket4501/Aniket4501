### ⚡ Performance as a Product Problem

Sometimes the best product improvement isn't a new feature.

My roadmap said engagement. The app took fifteen seconds to open. Anything shipped onto that only ever gets measured on the people patient enough to wait, so I held my own roadmap for eight weeks and put launch time first.

- App launch time: **15s → under 2s**
- Bundle size: **25MB → 6MB**

### 🔬 What I Build When Nobody Hands Me a Roadmap

**[Grounded](https://aniketagarwal-com.vercel.app/lab/grounded)** is an evaluation harness that scores LLM-generated health summaries against a rubric you can read: grounding, scope, escalation, readability. Every check is a deterministic rule, so it runs in your browser with no model call and no API key.

Its first run disagreed with my own labels on 5 of 16 cases. On 4 of those, the harness was wrong, not the labels. Both versions are still in the repo so a change can be diffed.

## 🔍 How I Think About Products

**Problem → Evidence → Hypothesis → Build → Measure → Iterate**

Before building anything, I try to answer:

- What problem are we actually solving?
- How do we know it's a real problem?
- Which users hit it hardest?
- What's the smallest thing that tests the hypothesis?
- What metric should move if we're right?
- What did we learn after shipping?

I like ambiguous problems where there isn't an obvious answer.
